## Task 1: Task-context integrity (R1, R2, R5)

**R1 — Cancelling the scope dialog must not advance the comparison baseline.** `src/pages/AnimalEditor/wiring/TaskTypesContainer.tsx`: `handleSave` compares the submitted definition against `modal.taskType` (line ~180, `contextChangeFor(modal.taskType, cleaned)`), and the scope dialog's `onCancel` (~344-352) reopens the modal with `taskType: { ...pendingContext.taskType, ...pendingContext.definition }` — the unsaved draft becomes the "original". Save → Cancel → Save again then asks nothing and rewrites history. Fix: the baseline for change detection and for pinning is ALWAYS the persisted catalog entry (`taskTypes.find((t) => t.id === editingId)`), never the modal's draft; keep the user's draft separately for reopening (e.g. a `draft` field on the modal state that `TaskTypeModal` uses for initial values). Tests: save → cancel scope → save again asks again; save → cancel → edit again → "keep earlier days" pins the ORIGINAL persisted environment and cameras (both fields).

**R2 — A room-only save must not reorder cameras.** `src/pages/DayEditor/EpochsTab.tsx` `TaskContextForm.handleSave` (~1594-1600) builds `nextCameras` by filtering the animal CATALOG, so `[1, 0]` becomes `[0, 1]`. The converter uses the FIRST task camera's calibration for position (`trodes_to_nwb/src/trodes_to_nwb/convert_position.py:1062`), so this can change position scaling. Fix: preserve the effective order for cameras that remain selected (start from `row.cameras`), remove deselected ones, append newly selected ones in catalog order; a save with no camera change yields an array identical to the effective one (so no override is written when it equals the default, order-sensitively). Tests: room-only edit on `camera_id: [1, 0]` keeps `[1, 0]` exactly and the merged day's first camera calibration is unchanged; reversed source order; a split-import day referencing `[2, 1]` with catalog `[0, 1, 2]` keeps `[2, 1]`; deselecting 1 from `[1, 0]` gives `[0]`; adding 2 to `[1, 0]` gives `[1, 0, 2]`.

**R5 — The shared review must show the same warning count as the gate.** `src/components/EffectiveDayReview.tsx:37` calls `buildPreflightSummary` without `warningCount` (defaults to 0 → "Non-blocking warnings: None") while `ExportPreview.tsx` shows "Ready to export · 2 warnings to review" from `vm.issues.filter(isAdvisoryIssue)`. Fix: `EffectiveDayReview` takes a required `warningCount: number` prop (or `issues` and derives it with the same `isAdvisoryIssue`); `ExportPreview` passes the gate's count; `DayStatusTable` (ValidationSummary) passes its per-day advisory count from the view-model. Tests: on a day with two real advisory issues the export page's readiness line and the review row agree ("2 warnings to review (does not block export)"); ValidationSummary shows the same.

CHANGELOG: one line under Fixed for R1 (history protection survives cancelling the scope dialog) and one for R2 (editing a day's room no longer reorders its cameras); R5 is internal consistency — fold into the R2 line or add a short one.
